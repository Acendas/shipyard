## Step 2: Execute Waves (stage_id: wave_N_dispatch)

**Before-evidence, once, at wave 1 (4.6).** The sprint review shows before and after. Before the first builder starts, for each `ui: true` story capture the screen as it is now when `shipyard-data ui doctor` reports a working adapter: `shipyard-data ui screenshot --url <the story's scene or URL> --story <id> --label before`; for a behavior story with an auto `user_flow_probe`, run it once and keep the output under `<SHIPYARD_DATA>/captures/before/<id>.log` (a failing probe is the expected "before"). Adapter `none` or no probe: skip with one line. Never a question, never a blocker.

**Collapse pass-through stages into one tick (speed, load-bearing for cost).** A boundary stage with nothing configured to run — `wave_<N>_build` with no `build_commands`, `wave_<N>_refactor` under the default `execution.refactor_scope: sprint` — still costs a full `/goal` re-entry if ticked on its own. Collapse those into the preceding advance with `--via`:

```
shipyard-data cursor advance execute wave_<N>_tests --via wave_<N>_build --via wave_<N>_refactor
```

Each hop still emits its own `pipeline_tick_completed` / `pipeline_tick_started`, so the terminal gate and wave invariants (event-log readers) see an identical trail; one illegal hop refuses the whole chain atomically. **Collapsible stages are a config-dependent CLI allowlist** — anything that dispatches an agent, runs a command, or produces a verdict is refused, so this is enforcement rather than the earlier prose request to collapse only no-op stages. Full contract: [references/pipeline-cursor.md](references/pipeline-cursor.md) § "Collapsing pass-through stages".

**ALWAYS delegate task execution to subagents** — every task runs in a fresh context window, keeping the orchestrator lean. The dispatch shape determines parallelism and delegation depth, not whether subagents are used.
**Dispatch shape.**

Read `execution_mode:` from SPRINT.md frontmatter — set at planning time by `/ship-sprint` Step 8, or absent on an older/hand-created sprint (fallback below). Vocabulary: `solo` / `task` / `track` are canonical; `subagent` (legacy alias of `task`) and `team` (legacy alias of `track`) are still accepted wherever a mode name is read. `--mode` always forces the shape named for this invocation, overriding the SPRINT.md value.

**A declared or forced mode is honored — full stop.** Execute the declared/forced mode. Do NOT silently override it, do NOT route to `escalating-to-thinker` (mode selection is not one of its seven triggers), and do NOT ask the user to re-confirm a mode they already declared. The incident behind this rule was a shell that silently dispatched `task` for a sprint declaring `track`; the fix is to honor the declaration, and honoring it needs no interrupt. Isolation is **per-mode, not universal**: `task`/`track` isolate each concurrent builder in its own worktree and integrate through the branch-based `verify-wave-integrated` gate; `solo` runs **sequentially in-place on the working branch with no worktree** — sequential work has no concurrent writer to race, so there is nothing for isolation to protect and the integration gate is vacuously satisfied (zero `shipyard/wt-*` branches). A forced mode that is genuinely unavailable in this session falls back with a one-line note, which is a statement, not a question.

**Isolation resolution (`--isolation`).** Do NOT hand-derive this from prose — call the CLI so resolution has one source of truth: `shipyard-data resolve-isolation [--flag <value>]`, passing the `--isolation` argument as `--flag` when the user supplied one (it accepts `true|false|worktree|none`). It prints exactly `worktree` or `none`, applying the precedence flag > `execution.isolation` in config.md > default `worktree`. Capture that once and carry it as the wave's `isolation` decision. When it prints **`none`**, dispatch **sequentially in-place** regardless of task count — this is the `solo` dispatch shape, chosen deliberately for a heavy build where a warm canonical checkout beats parallelism. No-isolation is **sequential-only by construction**: parallel builders on a shared checkout would clobber each other's edits and there is no per-task `shipyard/wt-*` branch for the wave-integration gate to rebase. If `--isolation false` is combined with `--mode task|track`, **coerce to sequential in-place and emit a one-line note** (`Isolation off forces sequential execution; running solo-shape despite --mode <m>.`) — a statement, not a question. When isolation is on, `task`/`track` behave exactly as today.

A "track" is the set of this wave's tasks that share a parent feature (read each task's `feature:` frontmatter field to group them) — computed fresh every wave regardless of dispatch shape, since track membership can vary wave to wave even when the sprint-level shape does not.

**Fallback (no `execution_mode:` in SPRINT.md).** Mirrors `/ship-sprint` Step 8's own heuristic: any wave with two or more steps → `task`; one step in every wave → `solo` (`shipyard-data sprint plan-score --json` gives `recommended_mode`). **Never auto-select `track`** — it is opt-in only (below), so a sprint that never declared a mode never lands in it.

- **`solo`** — a single task, or a wave whose tasks are all trivial (no shared track worth the coordinator overhead). Dispatched **sequentially** on the same branch, no worktree isolation.
- **`task`** (alias `subagent`) — worktree-per-task isolation plus branch-based integration (`verify-wave-integrated`); the shape for build waves with no meaningful track. Dispatch **parallel**: every step of the wave gets its builder at once. The only ceiling is `execution.max_agents` (default 100 agents alive at the same moment, all kinds counted together), and the agent hook enforces it: a spawn it refuses is not an error, wait for a return and spawn that builder then.
- **`track`** (alias `team`) — **experimental opt-in only; never auto-selected.** Native nested Agent behavior has known completion-routing and ownership risks, so this mode is not the default fast path. Prefer flat `task` mode unless the user explicitly requested track-mode soak. A forced/declarative `track` run must first read `${CLAUDE_PLUGIN_ROOT}/skills/ship-execute/references/track-mode.md`; if the platform cannot satisfy its probe/fallback contract, fall back to flat queued workers with a one-line note rather than spawning nested builders.

### Proactive Queue Dispatch (task mode fast path)

For normal `task` mode waves, main enqueues the wave's tasks before spawning workers:

```
shipyard-data queue enqueue --pipeline ship-execute --stage wave_<N>_dispatch --input <wave-work-items.json> --require-isolation <resolved worktree|none>
```

**Include each item's `effort`** (from the step file's `effort:` frontmatter) in the work-items JSON. Under the default `execution.dispatch_order: critical_path`, `queue enqueue` sorts the wave longest-effort-first (XL→L→M→S, task-id tie-break) so the long pole overlaps the short work instead of running alone in the wave's tail — `claim` hands out array order, so enqueue order *is* dispatch order. This is CLI-enforced, not a prose request: omitting `effort` just sorts that item last, it never fails the enqueue. Merge order at the wave boundary stays task-ID order regardless.

**A step a person does at the end (`needs_person: after`) is never dispatched.** At its wave, record it as waiting: `shipyard-data step set-status <PID> blocked --reason waiting_for_person`. It does not count as a parked step, and the sprint review collects it. Leave it out of the wave's work items.

Then spawn one leaf worker per step in enqueue order (all of them; the agent hook refuses a spawn only when `execution.max_agents`, default 100, are already alive), each **named `builder-<step id>`** and told to claim that step (`--task`): the name is then the address for `SendMessage` (warm fixes, relayed `INTERFACE` notes) and the label in the agent ledger. Each worker prompt must say:

```
Claim exactly your item:
shipyard-data queue claim --pipeline ship-execute --stage wave_<N>_dispatch --worker builder-<step id> --task <step id>

If claimed=false, return immediately. If claimed=true, perform only that item
directly in this worker context and record the result with ONE command:
shipyard-data task-return <step id> status=COMPLETE|BLOCKED commit=<sha> probe-exit=<code> output-tail-file=<path> --data-dir <data_dir>
It writes the return artifact AND closes your queue item. Do not run `queue complete` (a worktree sandbox may refuse it).
Only when you could not start the work at all:
shipyard-data queue fail <task-id> --pipeline ship-execute --stage wave_<N>_dispatch --worker <worker-id> --reason "<short reason>"

Never spawn another Agent. Never invoke /goal. Never call a capability skill as a nested dispatcher. Return only task id, status, and artifact path.
```

### Pre-spawn Branch Check (task AND track mode)

Before spawning any worktree agents, verify the orchestrator's branch: `git branch --show-current`, and read `branch` from SPRINT.md frontmatter.

- **On a `shipyard/wt-*` branch** → the orchestrator is inside a leftover worktree or the user checked out a worktree branch; new worktrees would branch from the wrong commit. `git checkout <sprint working branch>` first. Report: "WARNING: Orchestrator was on worktree branch [name], switched to [working branch]."
- **Branch doesn't match SPRINT.md** → `git checkout <branch>` first.

The WorktreeCreate hook branches worktrees from the current local branch — a wrong orchestrator branch forks every worktree from the wrong place.

**Read and follow** `${CLAUDE_PLUGIN_ROOT}/skills/ship-execute/references/task-dispatch.md` § Task Kind Routing, § Per-task dispatch and § Post-Subagent gate for every dispatch (shared with `--task` / `--hotfix`).

### Messages from builders (any wave stage)

Builders may send two kinds of message while they work (their agent body defines them); handle each when it arrives, in a line or two, without leaving the current stage:

- **`INTERFACE <step>: …`** — relay it with `SendMessage` to every live builder of this wave whose step touches the same module, file or contract (the step files' Technical Notes name them; when unsure, relay to all of the wave's live builders — it is one line each), and add it to the wave notes so the next wave's briefs carry it. Log `shipyard-data events emit interface_change_relayed step=<step> to="<names>"`. This is the default-mode version of what track mode's coordinator did; it exists because parallel builders drift on shared contracts and the merge is the worst place to find out.
- **`QUESTION <step>: …`** — answer through the Unattended decision ladder (SKILL.md: already decided → rule → consult → the builder's own recommended answer) and reply with `SendMessage` to that builder; log `execute_decision source=<...> subject=<step>`. Never forward it to the user.

### Wave waiting handler (stage_id: wave_N_waiting)

`pending_subagents` is a progress mirror for the worker ids spawned this wave; the queue ledger is the authority. Do not infer completion from Agent notifications. Track mode maintains a separate per-track handle/timeout list only when the experimental track coordinator is explicitly used; flat task mode uses the queue list below.

When `/goal` re-enters at `wave_<N>_waiting`:

1. Run `shipyard-data queue requeue-stale --pipeline ship-execute --stage wave_<N>_dispatch`, then `shipyard-data queue list --pipeline ship-execute --stage wave_<N>_dispatch`.
2. Interpret queue statuses:
   - `pending` → spawn a leaf worker for each pending step (the agent hook holds the `execution.max_agents` limit), then self-loop `wave_<N>_waiting`.
   - `claimed` with an unexpired `deadline_at`, or past it but listed in `requeue-stale` output `live` (recent `task_loop_iteration` since the claim) → still in flight; self-loop `wave_<N>_waiting`.
   - listed in `requeue-stale` output `completed_unacked` (completion event since the claim but the queue item never closed: worker died or the CLI refused) → NOT in flight, never self-loop on it. Run `shipyard-data queue reconcile <task-id> --pipeline ship-execute --stage wave_<N>_dispatch`: it moves the item to `complete` when `.subagent-returns/<task>.json` is a valid artifact (the recovery handler then runs the normal gate on it), or to `failed` with reason `completed_unacked_artifact_missing` (treat as BLOCKED/contract violation: mark `needs-attention`, emit `task_dispatch_returned status=blocked`). Either way the item is terminal and a later `requeue-stale` no longer reports it. `park-stale` does NOT accept a claimed item.
   - `stale` or failed non-idempotent stale item → if replay is explicitly safe, run `shipyard-data queue retry-stale <task-id> --pipeline ship-execute --stage wave_<N>_dispatch --reason "<why replay is safe>"` and self-loop; otherwise run `shipyard-data queue park-stale <task-id> --pipeline ship-execute --stage wave_<N>_dispatch --reason "worker_stale_non_idempotent"`, mark the task `needs-attention` with reason `worker_stale_non_idempotent`, emit `task_dispatch_returned status=blocked`, then continue after removing it from the pending mirror.
   - `failed` → route through the blocked/escalation handling from the task-loop gate (Blocked Task Handling, `references/task-dispatch.md`), emit `task_dispatch_returned status=blocked`, and do not redispatch more than once.
   - `complete` with `artifact_status: COMPLETE` → queue for `wave_<N>_recovery`; the artifact at `task.result` is the only accepted return surface.
   - `complete` with `artifact_status: BLOCKED` → route through the blocked/escalation handling from the artifact JSON; the worker returned a valid contract, but not a passed task.
3. If any queue item is `pending` or `claimed`, advance `→ wave_<N>_waiting` with `pending_subagents` rebuilt from the not-yet-terminal queue items (`task_id`, `worker_id`, `deadline_at`). Echo and exit.
4. If all queue items are terminal (`complete`, `failed`, or `stale` already parked), advance `→ wave_<N>_recovery`.

**Presumed-dead salvage stays in the wrapper.** The cursor-tick detector is read-only: it only emits `subagent_presumed_dead` and prints one line. When that event carries `completed_unacked=true` the builder finished: do NOT TaskStop, anchor or park; reconcile with `queue reconcile` and the return gate. For a genuinely dead builder, TaskStop, the salvage anchor and parking (`needs-attention`, reason `presumed_dead`) happen in the wrapper (this skill / `dispatching-task-loop`), never in the detector.

### Wave recovery handler (stage_id: wave_N_recovery)

Reads each completed queue item's result artifact and runs the orchestrator-side gate:

1. Run `shipyard-data queue list --pipeline ship-execute --stage wave_<N>_dispatch`; for every `status: complete` item (including items `queue reconcile` completed from a `completed_unacked` claim; `reconciled: true`), read `task.result` as JSON. Required fields: `task`, `status` COMPLETE|BLOCKED, `commit_sha`, `probe_exit_code`, `escalation_code`, `output_tail`, and `capture_file`. A missing, relative, unparseable, or mismatched artifact is a contract violation (treat as BLOCKED). Never regex for `STATUS:` lines from worker chat.
2. **Run the orchestrator-side gate per task from the JSON fields** — follow `dispatching-task-loop`'s "Orchestrator-Side Parsing and Gating" section verbatim: sha `cat-file` verify, PROBE_EXIT:0 check, non-empty output tail, anti-stub-scan on the diff, and on pass `shipyard-data step accept-return <task> sprint=<sprint_id> wave=<N> commit=<sha> --data-dir {{data_dir}}` so the complete-path anchor, `task_dispatch_returned status=complete`, and task `done` mutation happen through the same bundled CLI choke point as sync mode. On `artifact_status: BLOCKED` or JSON `status: BLOCKED`, use the escalation-code routing + the blocked-return `task_dispatch_returned status=blocked` emit. That section is the single orchestrator choke point; do not fork its logic. Missing bundled acceptance orphans commits and starves the terminal gate.
3. **Decide next stage** (before routing to `wave_<N>_redispatch_iter_1`, **Read and follow** `${CLAUDE_PLUGIN_ROOT}/skills/ship-execute/references/task-dispatch.md` § "wave_N_redispatch_iter handler" — it owns the per-task `dispatch_attempt` emit and redispatch model resolution): all COMPLETE + all gates pass → `wave_<N>_boundary`; any BLOCKED → `wave_<N>_redispatch_iter_1 iteration=<n+1> --trigger blocked`, gate failure → `... --trigger gate_failure`; TIMED-OUT tasks are already `needs-attention` (no re-dispatch).

## Step 4: Wave Boundary Check (stage_ids: wave_N_boundary → _build → _refactor → _tests → _verify → _gate)

Each numbered item is its own stage; the cursor advances stage-by-stage. `/goal` re-enters between stages until a terminal/paused/escalated marker stops it.

1. **Rebase + ff-merge, then gate, then tear down — in that order.** Integrate first, verify integration, then remove worktrees. Tearing a worktree down before its branch is merged orphans verified task commits.
   a. **Integrate each `shipyard/wt-*` branch of a GATE-PASSED task**, one at a time in task-ID order: `git rebase <working-branch>` → `git checkout <working-branch>` → `git merge --ff-only`. **Do NOT remove the worktree yet.** Conflicts → render the conflict as chat text first (branch name, conflicting file list, the relevant `git status` lines — git output you read is not shown to the user until you print it), then resolve it without asking: `git rebase --abort`, send the conflict to the builder that wrote the branch (`SendMessage` to `builder-<step>`: rebase onto the working branch, keep both behaviours, re-run your step's tests, return the new sha — one attempt, it is still resumable until its wave's gate), and merge the result. If that fails, park the step (`needs-attention`, branch anchored as below) and log `execute_decision source=parked`. `AskUserQuestion` only when `execution.unattended: false`; never fall back to a regular merge (creates fork lines). **A parked task's branch (timed-out / persistent-BLOCKED, marked `needs-attention`) is NOT merged** — salvage it instead: `shipyard-data anchor-commit <task> <sha-of-branch-tip>` → `git worktree remove --force <path>` → `git branch -D shipyard/wt-<name>` (safe: anchored), so `verify-wave-integrated` Check A passes without merging unverified work.
   b. **Gate before teardown:** `shipyard-data verify-wave-integrated`. Over git ground truth (never the unreliable `worktreeBranch` field) it proves every live `shipyard/wt-*` branch is merged into the working branch AND no `COMPLETE` return commit is dangling.

      It deliberately does **not** require a task's originally-returned sha to be an ancestor of the working branch — the boundary rebase legitimately rewrites those shas, so a returned commit reachable via `shipyard/keep-*` is accepted. See `verifying-wave-completion/references/invariants.md` invariant 2 before changing this; requiring ancestry deadlocks every rebased wave.

      Exit 0 → it emits `wave_integration_verified`; proceed to (c). **Exit 3 → HARD STOP, CLI-enforced:** `cursor advance execute wave_<N>_build` is refused (exit 3, `--force` included) while the latest integration event in this boundary is `wave_integration_failed`; only a later `wave_integration_verified` clears it. Do NOT remove any worktree (work is safe on the `shipyard/wt-*` branches + `shipyard/keep-*` anchors). Integrate the named branches and re-run the gate once; if that one documented remediation doesn't clear it, follow the `escalating-to-thinker` playbook (trigger: `integration_gate`, subject: the wave / named branches); only if it declines, returns low confidence, or its recommendation also fails, render the gate's stderr output — the named un-integrated branches and dangling commits — verbatim as chat text, then AskUserQuestion. CLI output you saw in a Bash result does not count as shown until echoed.

   c. **Tear down only past the gate:** per merged branch, `git worktree remove` → `git branch -d shipyard/wt-<id>` (`-d`, never `-D`: refuses an unmerged branch — the final backstop). Then `shipyard-data clean-worktrees` as a sweep.
2. **Clean orchestrator branch.** `git status --porcelain` must be empty after merges. Legitimate state changes (task status frontmatter) → commit `chore(shipyard): wave [N] state update`. Never include manual PROGRESS.md edits.

   For anything left over, **classify before asking**: `shipyard-data readiness-check --classify <paths...>`. `ignored` and `generated` entries (build output, OS junk, a regenerated lockfile) are routine churn — clean or commit them with a one-line note, no ask. Ask ONLY when `source` is non-empty, and then print that list as chat text first; a `git status` line you read in a Bash result is not shown to the user until you print it.
3. **Integration boundary passed.** Do not emit `wave_check_passed` here: that event means the full wave completion gate passed, including build/refactor/tests/spec verification below. `shipyard-data verify-wave-integrated` already emitted `wave_integration_verified` as the structural integration signal.

   **Overlap (`execution.overlap_waves: true`, default, 4.5; CLI-enforced since 4.7.1).** Wave N is merged, so wave N+1 can start now instead of after N's build, tests, review and fixes. `cursor advance execute wave_<N>_build` is **refused** until wave N+1 has been dispatched (worktree isolation, a next wave exists) — the refusal prints the two commands to run. If a wave N+1 exists in SPRINT.md and the event log has no `pipeline_tick_started stage=wave_<N+1>_dispatch` yet: run Step 2 for wave N+1 **first** — `shipyard-data cursor advance execute wave_<N+1>_dispatch wave_number=<N+1> iteration=1 stuck_counter=0`, enqueue and spawn its builders from the merged HEAD exactly as Step 2 says, `pending_subagents` updated — then **step back into wave N's trailing lane**: `shipyard-data cursor advance execute wave_<N>_build wave_number=<N>` (the graph's one retreat edge, dispatch(N+1) → build(N)). Items 3b to 8 below then run for wave N while N+1's builders work; their fix steps (`wave_<N>_redispatch_iter_*`, patch steps from 3b) land on the working branch and N+1's branches rebase onto them at N+1's own boundary. Wave N+1's builders, wave N's reviewers and any fix builder all count toward the one `execution.max_agents` limit. With `overlap_waves: false`, or when no wave N+1 exists, or when N+1 was already dispatched (this boundary is a redispatch pass): **→ `wave_<N>_build`** directly.

   **3b. Per-story review (F028, `execution.story_review: true`, default).** For each story in SPRINT.md whose LAST step merged in this wave (`shipyard-data story-review check --json` lists `complete: true` stories with `settled: false`), review it now, while it is fresh, and sequentially — no builder runs during this item. **A UI story with an approved design (4.8):** run `shipyard-data ui verify --level screen --story <story>` (`--scene <name>` or `--image <frame.png>` when the design names no scene). For an exact snapshot its verdict is the verdict. For a mockup it writes a side-by-side image: Read it (design left, delivered right), list every difference by zone as findings, and put the image path in the spec reviewer's brief. Record the outcome on the review with `--design MATCHES|DIFFERS [--design-findings <n>]` (`UNVERIFIED --note "<why>"` only when the screen cannot be rendered here) — `story-review record` refuses a designed UI story without it, and a screen that differs is fixed in the sprint or the design is re-approved by the owner, never waved through. **Then score the risk (E004):** `shipyard-data risk score --base <sprint base> --head <HEAD> --story <story> --cap` — the CLI reads git, never the builder's claim, scores the files that story's own steps changed (not its siblings' in the same wave), and combines diff size, missing tests, churn, baseline floors and the profile's harms by MAX. Pass its `review_level` as the reviewers' `effort` when it is higher than `resolve-model think` gives; `required_checks` go into the spec-review brief as must-verify items; `human_gate: true` is honored at `/ship-review` Stage 5, not here: record the verdict with `--note "human gate: deferred to review"` and log `execute_decision source=rule decision="human gate deferred"` (with `execution.unattended: false`, confirm it in one `AskUserQuestion` first; add `--note "human gate: confirmed"`); exit 3 (the per-sprint critical cap) stops this item: `cursor escalate execute reason=risk_cap_reached`. **For a UI story (`ui: true`, E005):** before the reviewers, write `<SHIPYARD_DATA>/ui/<story>/screen.json` (`{"url": <screen URL>, "width": 375}` — the approved design snapshot is the implicit baseline) with the Write tool and run `shipyard-data ui verify --level screen --spec <that file> --story <story>`; exit 3 is a FINDING for the spec reviewer (deviation from the approved design, or a design-lint error), never something to re-run until green. Then follow the `dispatching-spec-review` playbook with `scope: "feature"`, `target_ids: [<story>]`, `base_ref` (sprint base), `head_ref` (current HEAD); then the `dispatching-gap-analysis` playbook with `scope: "feature"` for the same story and the spec-review findings as `evidence_paths`; **and the story's code review (4.6, `execution.code_review`, default on):** the `dispatching-code-review` playbook with `scope: "feature"`, `target_ids: [<story>]`, the same refs, all concerns (security, bugs, silent failures, patterns, tests, observability, data), at the risk score's `review_level` — it can run beside the gap analysis (both read-only). Code review belongs here, not in `/ship-review`: a finding is cheapest to fix while the builder that wrote the code is still resumable. Record the outcome through the CLI — `shipyard-data story-review record <story> --verdict approve|changes --spec PASS|FINDINGS --gaps <n> --code CLEAN|FINDINGS --code-findings <n> --head <HEAD sha>` — never by hand (the CLI refuses a record without `--code`). **FINDINGS are dispositioned by the Unattended decision ladder (SKILL.md), never by a question:** a finding that touches an acceptance scenario, the approved design, a probe/checklist gap or correctness becomes a patch step **in this sprint** (allocate `next-id steps`, write the step file, `patch_step_created source=story-review`, and have the step also fold the behavior into the story's acceptance criteria/Interface; under overlap the step joins the earliest wave whose builders have not been dispatched yet, or a new final wave appended to SPRINT.md — never a wave already running); only a `severity: low` finding (cosmetic, nothing a scenario or the design promises) goes to the backlog as a bug story or is accepted with the reason. Then `shipyard-data story-review disposition <story> --via patch_steps|bug_story|needs_attention|accepted --ids <...>` and `shipyard-data events emit execute_decision stage=wave_<N>_boundary subject=<story> source=rule decision="<n> findings → patch step <id> | bug story <id> | accepted" rationale="<severity/why>"`; a `changes` verdict without a disposition blocks the sprint terminal. Stories with steps still in flight wait for their own wave; item 7 (wave VERIFY) keeps its wave-scope pass for them. When `review.workflow: true` (F033) and more than one story completes in this wave, run the spec-review + gap-analysis pair through the `Workflow` tool with the per-story template in `${CLAUDE_PLUGIN_ROOT}/skills/ship-review/references/workflow-fanout.md` (read-only agents only; each story is still recorded with `story-review record` the moment its pair returns; a null entry falls back to the plain playbooks). The sprint-level review reads these records and does not repeat per-story findings. `verify-wave-integrated` is untouched by this item.

   **Scoped command resolution (`build_commands.scoped` / `test_commands.scoped`, used by items 4 and 6 below).** When a `.scoped` key is configured, substitute `{base}` with the wave's base sha (pre-wave HEAD — the sha this wave's worktrees branched from) and `{files}` with the wave's changed files (`git diff --name-only <base>..HEAD`, space-separated, working-branch-relative paths) before dispatching that command. **Widen to the full unscoped tier (`.full`/`.unit`, unsubstituted) and emit `shipyard-data events emit test_selection_widened stage=<stage_id> reason=<r>`** — never narrow on uncertainty — when ANY of:
   - the `{base}`/`{files}` placeholder cannot be resolved (no recorded wave base sha, or the `git diff` fails);
   - the scoped command itself errors when probed (a non-zero exit from a list/dry-run mode, where the runner has one);
   - the selection would be EMPTY. **Exit code alone cannot detect this** — `jest --passWithNoTests` exits 0 on zero matches and `vitest related` exits 0 unconditionally on zero matches (probe-confirmed) — so use list-mode first where the runner supports one (`jest --listTests`, `vitest list`) and treat zero listed files as empty; where no list-mode exists, widen rather than guess;
   - the wave's diff touches a lockfile or a global/root-level config path outside any changed file's own module boundary (e.g. `package-lock.json`, `go.sum`, `Cargo.lock`, a root `build.gradle`) — a scoped run cannot prove those are safe to skip;
   - the substituted command would exceed the Windows ~8K argument-length limit.

   When `.scoped` is unset, this whole procedure is skipped and the existing `.full`/`.unit` fallback runs unchanged — byte-identical to today's behavior for every project that hasn't configured `.scoped`.

   **Wave build/test de-duplication (exact-proof only).** Resolve the wave build command and wave test command before dispatch. If the final resolved command strings are byte-identical, run it only once at `wave_<N>_build`, then at `wave_<N>_tests` reuse the build capture/exit as the wave probe evidence and emit `shipyard-data events emit wave_probe_reused wave=<N> source=build reason=identical_command`. Do not dispatch the same command again. This is intentionally **exact equality only**: a build command that merely appears to contain tests, or a scoped selector that cannot be rendered deterministically, is not proof; run the test stage normally. The `wave_N_gate` still receives `wave_probe_capture` and `wave_probe_exit_code`, so no completion invariant is weakened.
4. **Wave-scoped build (stage_id: wave_N_build)** — if `build_commands.scoped` is configured, substitute and dispatch it per the resolution procedure above; else if `build_commands.full` is configured, dispatch it unscoped; either way follow the `dispatching-operational-task` playbook. If the resolved wave test command is byte-identical to the build command, retain the build capture path and exit code for `wave_<N>_tests` reuse. Failure → re-dispatch it for a bounded fix loop (`→ wave_<N>_build_fix_iter_1`). **If unconfigured, still advance as a pass-through tick** (the graph has no skip edges). **→ `wave_<N>_refactor`.**
5. **Wave REFACTOR + MUTATE (stage_id: wave_N_refactor)** — **runs only when `execution.refactor_scope: wave`.** Under the default `sprint` scope this is a pass-through: collapse it (`--via wave_<N>_refactor`) and refactor once at `sprint_refactor` instead. When it does run: dispatch a `general-purpose` subagent with an inline wave-refactor prompt (read the combined wave diff, dedupe + rename + add helpers, run a small mutation check, commit if changes). **Model + effort (simplifier):** Run `shipyard-data resolve-model simplifier` — it prints exactly one line `model=<m> effort=<e>`; pass each value as a string on the Agent call and OMIT any field whose value is empty (inherit). Never hardcode a model literal or re-derive the tier from config.md by hand. Log it once: `shipyard-data events emit dispatch_model_resolved role=<role> model=<model or inherit> effort=<effort>` (a logging failure never blocks the dispatch). Not a wave blocker — on failure emit `task_status_changed type=refactor_failed` and advance. **→ `wave_<N>_tests`.**
   **A wave made only of fix steps skips its build and its test run (4.0).** When every step of wave N is a fix step (created by `patch_step_created`), go straight to verify: `shipyard-data cursor advance execute wave_<N>_verify --via wave_<N>_build --via wave_<N>_refactor --via wave_<N>_tests`. Each fix step's own check already ran in its builder, the review in `wave_<N>_verify` still reads the change, and `sprint_full_build` / `sprint_full_tests` cover everything once at the end. The CLI allows this collapse only for such a wave; `execution.patch_wave_tests: wave` turns it off. Put fix steps found at the same boundary into ONE wave, never one wave each.
6. **Wave-scoped tests + single fix (stage_id: wave_N_tests)** — **Collect every failure in one run (4.5):** a runner that stops at the first failure hides the rest, and fixing them one per full-suite run cost a real sprint a multi-minute suite per stale test. Run the command in its keep-going form (`make -k`, no `-x`/`--bail`/`--fail-fast`; set it once with `shipyard-data config set test-commands-unit "<cmd>"`), read the complete failure list from the capture, and dispatch ONE fix for the whole list (one per unrelated cause at most), then one confirming run. **The confirming run is the tests that failed, not the whole suite (4.0):** run `test_commands.rerun_failed` when it is set, else each failed test by its own command (the way the fix step's probe runs it), and record that capture as the wave's test proof (`wave_probe_capture` / `wave_probe_exit_code`). Run the whole suite again here only when the runner cannot run a test by name. What a fix breaks elsewhere is caught by the next wave's test run and by `sprint_full_tests`, both on the merged code; a seven-story sprint ran its ten-minute suite four times inside one boundary to learn that. **Evidence instead of a second run (4.0):** every green `shipyard-logcap run` records itself as proof of that command on that code, and a test tier is run with `--reuse`, which skips a command already proven on this exact code (`PROVEN, not run again`, exit 0: a green run). So the last wave's whole-suite run is the sprint's final proof when nothing was committed after it, and `shipyard-data verify check --key <any name> --command "<the command>"` finds a proof by its command whatever it was recorded under. Nothing is recorded by hand here. first check the exact-proof reuse from item 4. If the resolved build/test command strings were byte-identical and the build capture exited 0, do not dispatch tests; set `wave_probe_capture` / `wave_probe_exit_code` from the build capture and emit `wave_probe_reused`. Otherwise, if `test_commands.scoped` is configured, substitute and dispatch it per the resolution procedure above; else follow the `dispatching-operational-task` playbook with `test_commands.unit` (today's fallback, unchanged). First time tests run for the wave's merged code unless the exact same command already ran green as the wave build; the operational task streams progress/failures via Monitor. Failure → ONE re-dispatch via `dispatching-task-loop` with the failing-test list as `continuation_note` (`→ wave_<N>_tests_fix_iter_1`); persistent failure emits `task_status_changed type=wave_tests_failed` and advances **to the wave gate — NOT past it**. "Advances" here means the stage graph moves to `wave_<N>_verify` → `wave_<N>_gate`; it does **not** mean the wave passed. At the gate, invariant 3 of the `verifying-wave-completion` playbook requires `wave_probe_exit_code == 0` — a persistently-red suite carries a non-zero `wave_probe_exit_code` and therefore **fails the gate** (ESCALATE: "the regression is real"). `wave_tests_failed` + advance only lets the gate adjudicate; it never permits shipping a red wave. **→ `wave_<N>_verify`.**
7. **Wave VERIFY (stage_id: wave_N_verify)** — follow the `dispatching-spec-review` playbook `scope: "wave"`, `target_ids: [task_ids]`, `base_ref` (pre-wave HEAD), `head_ref` (current HEAD). From the structured verdict run `shipyard-data verify findings --wave <N> --tasks <P001,P002> --met <n> --partial <n> --missing <n> --over-built <n>` (counts only, never finding text; the CLI rejects any other flag) BEFORE advancing or re-dispatching. FINDINGS → single re-dispatch per task via `dispatching-task-loop` (`→ wave_<N>_redispatch_iter_1 iteration=<n+1> --trigger verify_findings`); persistent gaps → `needs-attention` and surface to `/ship-review`. **→ `wave_<N>_gate`.**
8. **Wave COMPLETION GATE (stage_id: wave_N_gate)** — first triage the ideas captured so far in the sprint (`shipyard-data idea triage …`, decision ladder rule 1): leaving this stage is refused while one is undecided. Then follow the `verifying-wave-completion` playbook with `wave_number`, `task_ids`, `data_dir`, `working_branch`, `wave_base_sha`, `wave_head_sha`, `wave_probe_capture`, `wave_probe_exit_code`. It runs the six-invariant composite check with bounded recovery for RECOVERABLE misses and structured escalation otherwise. Only this gate emits `wave_check_passed wave=<N>`, and only on `STATUS: COMPLETE`.

   **Recovery note — the outer cursor must NOT duplicate this bounded recovery.** `verifying-wave-completion` has its OWN internal recovery budget. From the outer cursor's view, `wave_N_gate` is ONE tick that either returns `STATUS: COMPLETE` (advance) or `STATUS: ESCALATED` (`cursor escalate`, AskUserQuestion, do not advance).

9. **Report and continue** — emit `Wave [N]/[M] ✓ [████░░░░] [done]/[total] tasks • → Wave [N+1]`. Under direct invocation: auto-advance into the next wave (no pause, no `/clear`, no "continue?"). **Overlap:** when wave N+1 was dispatched at this wave's boundary (item 3), **→ `wave_<N+1>_waiting`** (`wave_number=<N+1>`; its builders have been running since then — go straight to the waiting handler). Otherwise **→ `wave_<N+1>_dispatch`** (`wave_number=<N+1> iteration=1 stuck_counter=0`), or if `N == M`: a sprint with **two or more stories** first gets its cross-story code review → **`sprint_code_review`** (`references/pipeline-sprint-complete.md` item 0a); a single-story sprint (already reviewed as a story) goes straight → **`sprint_refactor`** (`stuck_counter=0`) under the default `execution.refactor_scope: sprint`, else **`sprint_full_build`**.

## Recovery & resume

Files are the source of truth — never rely on conversation memory for wave/task state. **The cursor + the event log are the position anchor across sessions — `TaskList()` is not.** `TaskList()` only ever reflects tasks created in the *current* session; on the resume path this section exists for, the session is almost always a new one, so `TaskList()` comes back empty for this sprint no matter how much progress happened before. Treat a non-empty `TaskList()` as a same-session convenience only — if `[sprint-<id>] Wave N:` tasks are already there, the last non-`completed` one is a quick hint, worth confirming against the cursor + event log before trusting. Treat an empty `TaskList()` as uninformative, never as "position unknown" or "nothing has run" — it is expected on a fresh session and Step 1's rebuild-on-resume rule (in `pipeline-start.md`) is what repopulates it for the user to see; that rebuild is downstream of this triage, not an input to it. The authoritative position is always the cursor's `stage:`, cross-checked against SPRINT.md and the event log (the task list is a mirror, never authority). Then triage by cursor state:

| Situation | Signal | Action |
|---|---|---|
| **Compaction recovery** | context cleared mid-run; cursor present | The cursor's `stage:` is authoritative — dispatch to that handler and resume. Absent cursor → rebuild from PROGRESS.md `current_wave` + step-file `status`, confirm `git branch`, resume from the first non-done task, then `cursor advance execute wave_<N>_dispatch --force` (a mid-wave stage is never an entry stage, so recovery always needs `--force`). Corrupted cursor (unparseable YAML / missing fields) → refuse: *"EXECUTE-CURSOR.md is corrupted. Run `/ship-status --repair` first."* |
| **Pause / resume** | `status: paused` | **Goal-inert** — `/goal` stops and never auto-resumes; resume is a USER decision. Resume ONLY on an explicit user resume/continue: read the paused cursor's `stage:` + body note, confirm `git branch` matches SPRINT.md `branch`; then `shipyard-data cursor resume execute` (flips `status` back to `in_progress` at the recorded stage) and continue from that stage. Track mode needs no special-case re-spawn here — coordinators are wave-scoped, not sprint-persistent (`references/track-mode.md` § "Pause / Resume"), so whichever wave the cursor resumes into simply dispatches fresh track coordinators as normal; there is no prior teammate identity to recreate. |
| **/goal-mode crash** | `status: in_progress`, no clean pause | The event log is the source of truth. Follow [references/resume-from-event-log.md](references/resume-from-event-log.md): scan for the last `wave_check_passed`, cross-check the registry, re-verify last-clean-wave invariants with `wakeup_budget: 0`, re-dispatch incomplete tasks, advance. Empty/corrupted log → refuse, run `/ship-status --repair`. |
| **Crash during `wave_N_waiting`** | cursor at `wave_N_waiting` from a prior session | The background agents died with that session — do NOT wait out their timeouts. Route the still-pending tasks straight to re-dispatch (`wave_<N>_redispatch_iter_1 iteration=<n+1> --trigger recovery --force`, per the handler); Step 0 salvage already recovered any worktree commits they committed. |

Step 0 (worktree salvage) has already run before any resume path. Works alongside `claude --continue`, which restores conversation but not project state — the cursor bridges the gap. HANDOFF.md is retired; the paused cursor is the single resume surface. Paused-duration accounting (`total_paused_minutes`) is not carried; the pause note is the record of when/why.
