# Shipyard Data Model — Single Source of Truth

## Data Location

**All Shipyard data lives outside the project** in the plugin data directory. Always resolve the path by running `shipyard-data` in Bash:

```bash
SHIPYARD=$(shipyard-data)
# Then use: $SHIPYARD/spec/stories/, $SHIPYARD/config.md, etc.
```

**NEVER:**
- Hardcode `.shipyard/` paths (legacy — data moved to plugin data in v0.5.0)
- Guess absolute paths or look in other worktrees/directories
- Use paths from other branches or worktrees
- Use `status` as a shell variable name — it's read-only in fish shell. Use `fstatus`, `task_status`, or `feat_status` instead

**ALWAYS** use `$(shipyard-data)` to resolve the path dynamically.

## Source of Truth Hierarchy

Every piece of data has exactly ONE authoritative location. All other files are **generated views** rebuilt from source files. Never manually sync data between files — regenerate the view instead.

## Source of Truth Hierarchy

### Story Files (`$(shipyard-data)/spec/stories/SNNN-*.md`)
A story is the deliverable: `type: feature` or `type: bug`. Pre-v4 records (`spec/features/FNNN-*.md`, `spec/bugs/BNNN-*.md`) are read in place as stories; new stories are always written under `spec/stories/`.
Authoritative for:
- `title`, `status`, `epic`, `story_points`, `complexity`, `feasibility`
- `rice_reach`, `rice_impact`, `rice_confidence`, `rice_effort`; `rice_score` is a cached derived value updated by `shipyard-data story set` when those four change, never hand-authored
- `token_estimate`, `dependencies`, `references`, `children`
- User story, acceptance scenarios (Given/When/Then), decision log
- `steps:` array in frontmatter (legacy key `tasks:`) — the builder steps (P###) that build this story
- for `type: bug`: `repro_steps`, `expected`, `actual`, `environment`, `severity`, `lane` (hotfix), `debug_task`

### Step Files (`$(shipyard-data)/spec/steps/PNNN-*.md`)
The hidden TDD builder unit `/ship-sprint` creates. Pre-v4 builder records (`spec/tasks/TNNN-*.md` with `type: task` and `kind: feature|operational|research`) read as steps until `shipyard-data migrate` renames them.
Authoritative for:
- `title`, `status`, `effort`, `dependencies`, `story` (parent ID; legacy key `feature`)
- What to build, acceptance criteria, technical notes

### Task Files (`$(shipyard-data)/spec/tasks/TNNN-*.md`)
Enabling work (`kind: spike | unblocker | study | debug | chore`) with an optional `parent:` of any kind. A task listed in a story's `dependencies:` blocks that story until it is `done`.
Authoritative for:
- `title`, `status`, `kind`, `parent`, `effort`, `dependencies`, findings

### Epic Files (`$(shipyard-data)/spec/epics/ENNN-*.md`)
Authoritative for:
- `title`, `description`, `status`
- **NOT** authoritative for which features belong to it — that's derived from feature `epic:` fields

### Idea Files (`$(shipyard-data)/spec/ideas/IDEA-NNN-*.md`)
Authoritative for:
- `title`, `status`, `source`, `promoted_to`, notes

## Generated Views (rebuilt from source, never manually edited for data)

### BACKLOG.md (`$(shipyard-data)/backlog/BACKLOG.md`)
- **Contains**: Ordered list of feature IDs + manual override notes
- **Generated columns** (read from story frontmatter on display): title, RICE, points, status, complexity
- **Only manually editable field**: rank order and override reasoning
- **Regenerated by**: Any skill that modifies feature status, estimates, or backlog membership

Structure:
```markdown
---
last_groomed: YYYY-MM-DD
---
# Backlog
| Rank | ID |
|------|----|
| 1 | S009 |
| 2 | S011 |
| 3 | S004 |

## Overrides
- S011 ranked above S004 despite lower RICE: [reasoning]
```

When displaying the backlog, read each story file to get title, RICE, points, status, complexity. Never store these in BACKLOG.md.

### SPRINT.md (`$(shipyard-data)/sprints/current/SPRINT.md`)
- **Contains**: Sprint goal, capacity, wave structure (task IDs grouped by wave), execution mode
- **Generated data** (read from task/story files on display): task titles, effort, status, feature titles
- **Sprint-owned data**: goal, capacity, wave groupings, critical path, swap log, dates
- **Regenerated by**: ship-sprint (plan), ship-execute (after task completion)

Structure:
```markdown
---
id: sprint-NNN
status: active
goal: ""
capacity: 20
branch: ""              # user's working branch — recorded by ship-execute on start
created: YYYY-MM-DD
started_at: null        # ISO 8601 — written by ship-execute on first wave start
completed_at: null      # ISO 8601 — written by ship-execute on sprint completion
total_paused_minutes: 0 # accumulated across all pause/resume cycles
---
# Sprint NNN

## Goal

## Waves
### Wave 1
- P001
- P002

### Wave 2
- P003
- P004

## Critical Path
P001 → P003 → P007

## Swap Log
| Date | Added | Removed | Reason |
```

When displaying the sprint, read each step file to get title, effort, status, feature parent. Never store these in SPRINT.md.

### PROGRESS.md (`$(shipyard-data)/sprints/current/PROGRESS.md`)
- **Contains**: Current wave number, blockers, session notes
- **Generated data** (read from step files on display): completion counts, task statuses
- **Progress-owned data**: current_wave, blockers, session log entries

Structure:
```markdown
---
current_wave: 1
---
# Sprint Progress

## Blockers
| Task | Reason | Since | Escalation |
|------|--------|-------|------------|

## Deviations
| Task | Type | What Changed | Why |
|------|------|--------------|-----|

## Patch Tasks (added during sprint)
| Task | Patches | Reason |
|------|---------|--------|

## Session Log
- [date] [summary of work done]
```

Task completion status lives in step file frontmatter (`status: done`). Count done tasks by reading step files, not by maintaining a counter.

## Status Workflow State Machine

One canonical set of valid transitions. All skills reference this — never hard-code transitions locally.

### Story Status (features and bugs)
```
proposed → approved → in-progress → done → released (or done → deployed → released when the project has a deploy step)
proposed → deferred (park it)
proposed → rejected (kill it)
approved → deferred
in-progress → approved (pulled from sprint, back to backlog)
deferred → proposed (revisit)
```

### Idea Status
```
captured → assessing → promoted (--to a story or an epic)
captured | assessing → rejected
captured | assessing → parked → captured | assessing | rejected
```
Legacy `proposed` reads as `captured`, `graduated` as `promoted`. `promoted` and `rejected` are terminal.

### Epic Status
```
proposed (template) → decided → refined → in-progress → done
refined ↔ decided, in-progress → refined
```

### Task Status (enabling work)
```
open → in-progress → done
open | in-progress → dropped → open
```

### Step Status (builder units)
```
pending → approved → in-progress → done
in-progress → blocked → in-progress → done           (blocked: waiting on an external dependency)
in-progress → needs-attention → in-progress → done   (needs-attention: full audit trail but non-convergent; needs a human decision)
in-progress → approved (deprioritized, back to backlog)
```

`pending` is the entry state; `done` is terminal (leaving it requires `--force`). Step status is a fixed allowlist (`pending | approved | in-progress | blocked | needs-attention | done`), not an enforced transition graph.

### Sprint Status
```
planned → active → completed
planned → cancelled
active → cancelled
```

## View Generation Rules

When any skill needs to **display** an aggregate view (backlog table, sprint board, status dashboard):

1. Read the index file (BACKLOG.md, SPRINT.md) for structure (ordering, wave grouping)
2. Read each referenced source file (story/step) for live data
3. Display the merged result
4. **Never write source data back to the index file**

When any skill needs to **update** data:
1. Write to the source file only (story or step frontmatter)
2. If the index file needs structural changes (reorder, add/remove ID), update the index
3. Do not propagate data fields to other files

## Deriving Epic Membership

To find all features in an epic:
```
Grep for `epic: E001` across `$(shipyard-data)/spec/{stories,features}/*.md` frontmatter
```
Do NOT maintain a `features:` array in epic files. It's always computed.

## Deriving a Story's Steps

Story frontmatter contains `steps: [P001, P002, P003]` (legacy key `tasks:`) — the list of step IDs. Step details (title, effort, status) are read from individual step files. The story file does NOT contain an inline step table.
