# Sprint completion: Step 5 items 0-4

**Read** `${CLAUDE_PLUGIN_ROOT}/skills/ship-execute/references/pipeline-start.md` § Step 1 checklist rules (Update on wave transitions, gated); follow at `sprint_complete_gate` for the `Sprint Complete & Demo Probes` task.

## Step 5 items 0-4: Sprint Completion (stage_ids: sprint_code_review → sprint_refactor → sprint_full_build → sprint_full_tests → sprint_demo_probes → sprint_complete_gate)

0a. **Cross-story code review (stage_id: sprint_code_review, 4.6)** — only for a sprint with two or more stories and `execution.code_review` on; each story's own diff was reviewed at its boundary, so this pass looks only at what a per-story review cannot see: interactions between stories (two stories changing the same module or contract, duplicated helpers, an invariant one story assumes and another breaks) and the sprint-wide concerns `security` and `data`. Follow the `dispatching-code-review` playbook with `scope: "sprint"`, `base_ref` (sprint base), `head_ref` (HEAD), and the brief line "per-story findings are already settled; report cross-story findings only". Findings go through the Unattended decision ladder: fixed here as patch steps (warm fix to the builder that owns the code when it is still resumable, else `dispatching-task-loop`), only `severity: low` to the backlog; self-loop `sprint_code_review iteration=<n+1>` until a pass is clean (two passes at most, then the ladder decides). Emit `shipyard-data events emit sprint_code_review_completed sprint=<id> findings=<n> fixed=<n>`. **→ `sprint_refactor`** (or `sprint_full_build` under `refactor_scope: wave`); the full build and suite after it validate the fixes.

0. **Sprint REFACTOR + MUTATE (stage_id: sprint_refactor)** — **runs only under the default `execution.refactor_scope: sprint`**; under `refactor_scope: wave` the per-wave passes already ran, so skip straight from the last `wave_<M>_gate` to `sprint_full_build`.

   **A surviving mutant that needs a test is a fix step in a new wave.** When the mutation check finds a behaviour no test protects and it is above low severity: write the fix step (`patch_step_created source=sprint-refactor-mutation`), append a wave to SPRINT.md, and `shipyard-data cursor advance execute wave_<N>_dispatch` — a legal edge from this stage; never force the cursor. The fix wave skips its own build and test run like any wave made only of fix steps, and the pipeline comes back here.
   **Resolve the scope with the CLI, not by eyeballing config.md:** `shipyard-data resolve-refactor-scope` prints exactly `sprint` or `wave` (same one-source-of-truth pattern as `resolve-isolation`; an unrecognized value resolves to the default, never silently to the other option). The stage graph permits both `wave_gate → sprint_refactor` and `wave_gate → sprint_full_build`, so this read is what decides the edge — capture it once at the last wave's gate and carry it.

   Dispatch a `general-purpose` subagent with the same wave-refactor prompt shape as Step 4 item 5 (`references/pipeline-wave.md`), scoped to the **whole sprint diff** (`sprint_base_sha`..HEAD): dedupe + rename + add helpers, run a small mutation check, commit if changes. Same resolution: `shipyard-data resolve-model simplifier` (omit an empty field, never hardcode a literal).

   **This stage is placed BEFORE the full build and suite on purpose** — it is non-blocking on its own failure, so the thing that actually catches a regression it introduces is `sprint_full_build` + `sprint_full_tests` running after it. Do not move it later. On dispatch failure emit `task_status_changed type=refactor_failed` and advance. **→ `sprint_full_build`.**

1. **Full build (stage_id: sprint_full_build)** — if `build_commands.full` configured, follow the `dispatching-operational-task` playbook (catches cross-module compilation errors scoped builds missed). If unconfigured, advance as a pass-through tick (collapsible via `--via`).

   **Runtime de-duplication with full-test tiers.** Resolve `test_commands.unit`, `.integration`, and `.e2e` before the build dispatch. If `build_commands.full` is byte-identical to any resolved test tier command, or if the build command contains a test tier as an exact shell segment separated by `&&`, then a clean build run is also clean proof for that tier. On build PASS, record ledger evidence for each proven tier using the build capture:
   ```
   shipyard-data verify record --key test_commands.<tier> \
       --command "<that tier's own resolved command>" \
       --exit 0 --capture <build capture path>
   ```
   and emit `shipyard-data events emit build_proves_test_tier tier=<tier> reason=<identical|embedded_segment>`. This closes the runtime drift case setup can only warn about: old or hand-edited configs where `build_commands.full` still runs the same expensive tests `sprint_full_tests` would otherwise run again. This proof is conservative: substring guesses, runner-name heuristics, or reordered shell fragments do NOT count. If it is not exact evidence, do not record and let `sprint_full_tests` run/check normally.

   **Failure → run the documented remediation before interrupting.** `dispatching-operational-task` is itself the fix loop: re-dispatch it once against the failing build, bounded by its own iteration cap. A build that goes green on that pass advances with a one-line note — no ask. Only if it is still red after that one bounded cycle: `shipyard-data cursor pause execute --note "sprint_full_build failed: <why>"` BEFORE AskUserQuestion (so `/goal` stops and does not re-run the whole build and re-ask), then AskUserQuestion. Render the failure evidence first — the failing command and the capture file's error tail — as chat text; content in the capture file or the operational-task return does not count as shown until printed. **→ `sprint_full_tests`.**
2. **Full test suite (stage_id: sprint_full_tests)** — resolve `test_commands.unit`, `.integration`, `.e2e` from config.md FIRST, before dispatching anything (a tier with an empty/absent key is skipped). **Check the verification ledger before grouping**: for each resolved tier, run `shipyard-data verify check --key test_commands.<tier> --command "<resolved command>"`. Exit 0 means a fresh proof already exists for this exact tree/command (possibly recorded by `sprint_full_build` because the build command proved that tier); skip dispatching that tier and include it in the summary as `reused`. Exit 3 means stale/missing; include it in the dispatch set. Then **Dedupe identical tiers before dispatching**: group the stale commands by exact string equality; each group maps one-or-more tier names (`unit`/`integration`/`e2e`) onto ONE distinct command, dispatched **once per distinct resolved command**, not once per configured key — a project whose `test_commands.integration` is byte-identical to `.unit` (a real customer's is) must not pay for the same run twice. Note both reuse and dedup in the tick's `--note`, e.g. `--note "unit reused from build proof; integration+e2e identical, deduped to 1 distinct run; distinct runs counted after reuse"`. For each distinct stale command, follow the `dispatching-operational-task` playbook with a synthetic `task_id` of `sprint-full-tests-<n>` (n = 1-based index over the distinct stale commands, in unit→integration→e2e order); the playbook records the absolute logcap capture path in `verify_output`. This is the only time an unproven entire suite tier runs. Persistent failure after the cap → re-dispatch via `dispatching-task-loop` per failing cluster (`→ sprint_tests_fix_iter_1`, K bounded at 1).

   **Record evidence on a clean pass — per-tier AND aggregate (P1 — closes the redundant re-run at `/ship-review`'s Stage 1a and its quality-gate checks, which check the per-tier keys, not the aggregate one).** When a distinct command's dispatch exits 0, record ONE ledger entry **per tier name that group maps to** — a deduped group covering two tier names (e.g. `unit`+`integration` identical) records TWO entries against the SAME command/exit/capture, one per `--key`, so review doesn't re-run the tier that was deduped away:
   ```
   shipyard-data verify record --key test_commands.<tier> \
       --command "<that tier's own resolved command — the tier's, even if identical to a sibling tier's>" \
       --exit 0 --capture <absolute logcap path from the operational task's verify_output>
   ```
   `<tier>` is the literal `unit`, `integration`, or `e2e` — the exact key names `/ship-review`'s Stage 1a and quality-gate evidence checks look up.

   Once EVERY resolved tier has either fresh ledger proof or a newly-run distinct command with exit 0, ALSO write a summary capture (`<SHIPYARD_DATA>/captures/sprint_full_tests/summary.log`: each tier, whether it was reused or run, its evidence source/capture path when known, and `exit 0`) and record the aggregate:
   ```
   shipyard-data verify record --key sprint_full_tests \
       --command "<distinct commands, unit→integration→e2e order, joined with ' && '>" \
       --exit 0 --capture <SHIPYARD_DATA>/captures/sprint_full_tests/summary.log
   ```
   `sprint_full_tests` is the exact literal key the terminal gate (`FULL_SUITE_KEY` in `bin/verify-ledger.mjs`) checks for release approval — do not rename it. Neither `verify record` call changes what the stage runs or its cursor advance — they only record proof of what already ran, so `/ship-review` can prove the suite already passed against this exact tree (via `shipyard-data verify check`) instead of re-running it. Skip BOTH the per-tier and the aggregate calls on any non-clean outcome — a stale/absent ledger entry is always safe (it just means the next reader re-verifies), a falsely-fresh one is not.

   **→ `sprint_demo_probes`.**
3. **Per-feature user-flow probes (stage_id: sprint_demo_probes)** — the cross-task proof that the feature works *for a user*; catches "all unit tests pass but the integrated feature doesn't work". Unit/integration/e2e-in-CI runs — step 2, just finished — do not exercise the path a user takes; that is what this stage is for. Read SPRINT.md `features:`, then each feature's `user_flow_probe:` (legacy scalar `demo_probe:` still reads as `kind: auto`; note the deprecation once per sprint and move on).

   Branch on `kind`:

   - **`kind: auto`** → get what to run from the CLI: `shipyard-data story probe-command <F> --json` prints `run` (the probe, without a trailing full test command whose proof is fresh for this tree: the suite is proven once per boundary, never once per story) and `record_as` (the probe's own command). Run `run`, record with `record_as`. Then follow the `running-acceptance-probe` playbook (`probe_command: <run> 2>&1 | tee <SHIPYARD_DATA>/captures/demo_probe_<F>/run.log`, `cwd: <working branch checkout>`, `timeout_seconds: 120`) — tee to a deterministic capture path so a PASS has a file to record against — then emit `acceptance_probe_completed feature=<F> probe_type=demo exit_code=<n> verdict=<PASS|FAIL|TIMEOUT|ERROR>`. **On `verdict=PASS`**, record ledger evidence: `shipyard-data verify record --key demo_probe.<F> --command "<record_as>" --exit 0 --capture <SHIPYARD_DATA>/captures/demo_probe_<F>/run.log` — so `/ship-review` Stage 4.8 can skip re-verification via `verify check` instead of always re-running the probe.

   - **`kind: assisted` / `kind: manual` while `execution.unattended: true` (default)** → a person's confirmation is collected at `/ship-review` Stage 5 (demo), not here. For `assisted`, still run `probe.command` (the setup) and tee it; a failing setup is FAIL below. Then emit `acceptance_probe_completed feature=<F> probe_type=demo exit_code=0 verdict=PENDING_HUMAN` and `shipyard-data events emit execute_decision stage=sprint_demo_probes subject=<F> source=rule decision="human probe deferred to review" rationale="unattended execute"`, and continue. Invariant 8 reads PENDING_HUMAN as pass-pending; the review's approval cannot complete until `story record-proof` has recorded the person's verdict.
   - **`kind: assisted` (attended, `execution.unattended: false`)** → run `probe.command` first (the setup: deploy to device, seed data, launch to the screen), tee to the same capture path. If the setup command itself exits non-zero, treat it as FAIL below — there is nothing for a human to look at. On a clean setup, **render `probe.steps` verbatim as chat text** (the steps exist only in a Read result until you print them — a bare ask here is the blind-ask bug), then `shipyard-data cursor pause execute --note "user_flow_probe assisted awaiting verdict for <F>"` BEFORE the AskUserQuestion: *"Feature [S###] is deployed and ready. Does the flow above work?"* Options: **Yes, works** / No, it's broken / Can't check right now.

   - **`kind: manual` (attended)** → no command to run. **Render `probe.steps` verbatim as chat text**, then pause (same `cursor pause` note with `manual`) and ask the same question.

   For `assisted`/`manual`, the answer is **evidence, not a skip** — record it:
   ```
   shipyard-data story record-proof <F> verdict=pass|fail confirmed-by=<user> commit=<sprint HEAD sha> answer="<their own words about this flow>" [note="<what they saw>"]
   ```
   which emits `user_flow_probe_confirmed` and satisfies Invariant 8 exactly as an exit-0 `auto` run does. "Can't check right now" records nothing and pauses the sprint — an unconfirmed flow is not a passing flow, and the cursor is already paused so `/goal` stops.

   - **`user_flow_probe: skip-with-reason`** with populated `user_flow_probe_skip_reason` → means *no proof of any kind exists* (a hand-checked flow is `kind: manual`, not this). Emit `acceptance_probe_completed feature=<F> probe_type=demo exit_code=0 skipped=true reason=<short>` and continue (Invariant 8: PASS-with-warning). **Also record ledger evidence**, so `/ship-review` Stage 4.8's `verify check --key demo_probe.<F>` finds a fresh entry and doesn't re-ask the same skip question every review: Write a small capture noting the skip (`<SHIPYARD_DATA>/captures/demo_probe_<F>/skip.log`: feature ID, `user_flow_probe_skip_reason`, timestamp), then `shipyard-data verify record --key demo_probe.<F> --command "skip-with-reason:<user_flow_probe_skip_reason>" --exit 0 --capture <that file>`. Decision: the recorded command is the skip marker, NOT the probe command itself — this deliberately does not claim any probe ran, so if a real probe is later authored for this feature, the commandHash mismatch invalidates the entry and forces a genuine run instead of a stale skip surviving past it.

   - **Probe absent entirely** → this is a **planning-gate escape**, not a decision to make here. `/ship-sprint` refuses to plan a feature without a `user_flow_probe`, and the Pre-flight `every_feature_has_user_flow_probe` gate (`references/goal-mode-preflight.md`, runs in every mode) re-checks it before wave 1 — so reaching this stage without one means one of those was bypassed. `shipyard-data cursor escalate execute reason=user_flow_probe_missing`, name the feature, and point at `/ship-discuss <F>` to author one. Do not offer to skip: authoring a probe *after* the sprint built is how the field ends up rubber-stamped.

   - **FAIL (any kind), unattended** → a failing user flow is a defect found in the sprint: ONE re-dispatch of the story's steps via `dispatching-task-loop` with the probe output tail as `continuation_note` (`patch_step_created source=user-flow-probe` when a new step is needed), re-run the probe; still failing → `shipyard-data cursor escalate execute reason=user_flow_probe_failed next_action="/ship-debug <F>"`. Log the `execute_decision` either way. Never record ledger evidence on this path.
   - **FAIL (any kind), attended** → render the probe command (or steps) and its output tail as chat text first — the probe result exists only in the capability skill's return until you print it. `shipyard-data cursor pause execute --note "user_flow_probe <verdict> for <F>"` BEFORE AskUserQuestion: *"Feature [S###] user_flow_probe returned [verdict]. (a) investigate via /ship-debug [S###], (b) abort and re-execute failing tasks, (c) override with `skip-with-reason` (recorded; review will flag)."* Do NOT proceed unless (c) with justification or the probe passes on retry. Do NOT record ledger evidence on this path — only a clean pass or a justified skip is proof.

   Same asymmetry as the per-tier/aggregate records above: a stale/absent `demo_probe.<F>` ledger entry is always safe (Stage 4.8 just re-verifies), a falsely-fresh one is not — so the `verify record` call is skipped on FAIL/TIMEOUT/ERROR and only ever fires on the PASS or skip-with-reason branches.
   - All PASS (or skip-with-reason) → **→ `sprint_complete_gate`.**
4. **Sprint-complete predicate (stage_id: sprint_complete_gate)** — first run `shipyard-data story-review check` (F028): exit 3 names stories whose steps are all done but whose per-story review is not settled — review and record them (Step 4 item 3b) before anything else; the execute terminal refuses otherwise (unless `execution.story_review: false`). Then follow the `evaluating-sprint-complete` playbook with `sprint_id`, `data_dir`, `working_branch`, `sprint_base_sha`, `sprint_head_sha` (current HEAD), `sprint_verify_capture` + `sprint_verify_exit_code` (from step 2), `demo_probe_event_window_start` (SPRINT.md `started_at`), `review_verdict_path: null`. This is the pre-review invocation: invariants 1–6, 8 and 9 MUST pass, invariant 7 is SKIPPED because review has not run yet, and invariant 3 accepts feature `status: in-progress` because `/ship-review` owns the transition to `done`. `STATUS: INCOMPLETE` → print the failing-invariant list (each invariant + why it failed, from the gate's return) as chat text, then escalate via AskUserQuestion — the list must appear in chat, not only in the question/option strings. `STATUS: COMPLETE` → step 5. **→ `terminal_handoff_to_review`.**
