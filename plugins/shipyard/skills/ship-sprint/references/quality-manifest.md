# Step 10: Quality Gate Manifest Generation

After adversarial critique (Step 9.7) and before presenting the sprint plan, generate the sprint's quality gate manifest.

## QUALITY-GATE.md

A derived artifact (like PROGRESS.md) at `<SHIPYARD_DATA>/sprints/current/QUALITY-GATE.md`. Never manually edited. Generated by `/ship-sprint` and consumed by `/ship-review` Stage 1.5.

## Structure

```yaml
---
sprint: sprint-NNN
generated: YYYY-MM-DDTHH:MM:SSZ
---
```

```markdown
## Standing Gates

| # | Gate | Verification | Status |
|---|------|-------------|--------|
| SG-1 | [description from config] | probe: [command] | pending |
| SG-2 | [description from config] | manual | pending |

## Sprint-Specific Gates

| # | Gate | Source | Verification | Status |
|---|------|--------|-------------|--------|
| SSG-1 | Timeout handling verified | F009 (timeout) | probe | pending |
| SSG-2 | Idempotency under retry | F009, F011 (idempotency) | probe | pending |
| SSG-3 | Graceful degradation | F011 (graceful-degradation) | manual | pending |

## Integration Gates

| # | Gate | Epic | Features | Verification | Status |
|---|------|------|----------|-------------|--------|
| IG-1 | User data flows signup→profile | E001 | F001, F003 | probe | pending |
```

## Generation Procedure

### Standing Gates

1. Read `config.md` `quality_gates.standing` array
2. For each gate, infer `verification_type`:
   - Gate text references a `test_commands` key (e.g., "All E2E tests pass (test_commands.e2e)") → `probe` with that command
   - Gate text references a specific tool name → `tool`
   - Otherwise → `manual`
3. Write one row per gate with `Status: pending`

### Sprint-Specific Gates

1. For each feature in this sprint, read its E2E AC (the `### E2E AC` section)
2. Group by `e2e_category`
3. For each unique category that appears across all sprint features:
   - Create one gate row referencing the category and all source feature IDs
   - `Verification` comes from the AC's `verification_type` field (use the most automatable type if features differ: probe > tool > manual)
4. Deduplicate: if F009 and F011 both have `timeout` E2E AC, create one timeout gate referencing both

### Integration Gates

1. For each feature in the sprint, check if its epic has Integration AC (`## Integration Acceptance Criteria`)
2. For each Integration AC that references features in THIS sprint, add a gate row
3. Skip if no epic integration AC reference this sprint's features

## Skip Condition

Skip manifest generation entirely if:
- Config has no standing gates (`quality_gates.standing` is empty or absent) AND
- No selected feature has E2E AC AND
- No epic integration AC reference this sprint's features

In this case, do not create QUALITY-GATE.md. Ship-review Stage 1.5 handles the absence gracefully (skips quality gate enforcement).

## EXTEND Mode

When `/ship-sprint` EXTEND mode adds or removes features, regenerate QUALITY-GATE.md to reflect the updated scope. Standing Gates remain unchanged; Sprint-Specific and Integration Gates are re-derived from the new feature set.

## Edge Cases

- **All verification_type: "probe"**: The manifest is fully automatable. Ship-review Stage 1.5 dispatches all gates as operational tasks.
- **All verification_type: "manual"**: The manifest becomes a pure checklist for ship-review Stage 5.
- **Empty manifest (skip condition met)**: No QUALITY-GATE.md created. This is valid — not every sprint needs quality gates beyond the standard test suite.
- **Feature has E2E AC but no probe authored yet**: Gate is created with `Status: pending`. The probe is authored during task decomposition (Step 4) by `authoring-acceptance-probe`.
