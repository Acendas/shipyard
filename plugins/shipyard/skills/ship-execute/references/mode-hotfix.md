1. Read bug file (S###). 2. **Derive the target branch** — default to the bug file's `branch:` frontmatter, else the current checkout. On disagreement, run `shipyard-data readiness-check --target-branch <bug file's branch>`: `must_ask: false` → apply the returned `switch_branch` action and state it in one line (the bug file is the record of which branch the fix belongs on, and switching a clean tree is reversible). Ask only when the CLI says `must_ask` — i.e. the tree is dirty or the branch doesn't exist. The verdict fields and the ask protocol: **Read** `${CLAUDE_PLUGIN_ROOT}/skills/ship-execute/references/pipeline-readiness.md`. 3. Execute TDD cycle (must include regression test). 4. Commit `fix(S###): [description]`. 5. **Terminal (stage_id: terminal_hotfix).** Print `Hotfix ready. Review with /ship-review --hotfix S###` first, then `shipyard-data cursor advance execute terminal_hotfix status=complete outcome=success reason=hotfix_ready next_action="Hotfix ready — handoff to /ship-review --hotfix"`. The CLI appends `pipeline_terminal`, re-renders PROGRESS.md, prints the `▶ CYCLE COMPLETE — pipeline terminal. /goal should stop.` marker as the final line; echo it.

**Parked hotfix (not success).** Still BLOCKED after the one redispatch: print `Hotfix needs attention — <reason>`, then `shipyard-data cursor escalate execute reason=task_needs_attention next_action="Resolve, then shipyard-data cursor resume execute"`; echo its stop marker. Never `Hotfix ready.`

Shipyard does not create branches, merge, or push for hotfixes — the user handles their own git workflow. Hotfix does NOT affect sprint state or velocity. Hotfix is the one exception that DOES run tests at task level — the regression test is the whole point, and you need red→green→still-red-after-revert→green to prove the fix catches the bug.
